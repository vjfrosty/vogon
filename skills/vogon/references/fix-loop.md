# Fix mode — loop to 8

Read this only in `fix` or `fix auto` mode, after step 5 of SKILL.md. Before the first fix, copy each target file to `.vogon/.tmp/start/<path>` (SKILL.md step 3); the growth check below measures against it. Repeat up to **3 rounds**:

1. **Plan the round:** one line per `fix` finding (`id — what will change, where`), plus every `needs-you` finding.
2. **Approve.** `fix`: one AskUserQuestion per round. Round 1 asks the decisions first: each `needs-you` finding as its own question (most important first, at most 3, each with 2–3 concrete options), then one question on the plan: apply all, pick ids, or stop. The answers are decided: write them into the fixes and add them to the settled list for every later critic. Later rounds ask about the plan and any new important `needs-you`. An unapproved `fix` becomes `declined` and leaves the score. `fix auto`: no question; print the plan as the round's log, and for each `needs-you` take the smaller, reversible option as a marked proposal.
3. **Apply** the approved fixes yourself: you have this conversation's context, which no agent has. Read whatever the target depends on (config, scripts, code a plan names) first.
   - **Fix the cause, not the sentence.** Change the mechanism that makes the finding true, not only the line it quotes: a plan that moves a database must also move what depends on its location (credentials, connection settings, roles, the services writing to it).
   - **Check what else relies on the same thing** (a host, port, secret, order of steps, file, version); if it would break the same way, fix it in the same edit. When something is missing (rollback, backup, certificate, timeout), add the step where it belongs, with the check that proves it worked.
   - **Stay inside the findings:** no restructuring or improvements no finding is about; prefer rewording or removing over adding.
   - A value only the user can set (a retention period, a deadline, a budget, who is on call) is never written as fact: write `14 days (proposed — confirm)` and add it to the To do list; that finding leaves the score. When a fix depends on something you cannot see, write the step so it checks that thing instead of assuming it.
   - Send all edits in one message.
   - **Keep a code fix only if you ran it.** Before the first fix, run the project's tests (or its build or type check when it has no tests) and log the result: `tests before: 90 passed, 15 skipped`. Run them again after each round. A fix that turns a passing test red is repaired or reverted. A code fix is checked only when something you ran exercised the changed lines: a test that ran (a skipped test checks nothing) or a command of your own. A code fix that nothing exercised does not stay in the code: `fix` asks whether to keep it unverified; `fix auto` reverts it, lists the intended change in To do as a proposal, and leaves the finding open. When nothing can be run at all, apply no code fix. Prose (docs, comments, a plan) needs no run.
   - Leave `taste` alone. Never commit: the user reviews the changes and commits them. Never undo with git (`checkout`, `restore`, `reset`, `stash`, `clean`): it also discards the user's own uncommitted work. Undo a fix with Edit, from the `.vogon/.tmp/prev/` copy.
4. **Growth:** the target may end at most about twice its starting length in words, so write each fix to fit that. After each round, log the word counts against the start copy (`wc -w .vogon/.tmp/start/<path> <path>`; in PowerShell, `(Get-Content <path> | Measure-Object -Word).Words`): `round 1: 231 → 390 words`. Count words, not lines: a line rewritten into a paragraph adds no lines. Past about double, this round is the last: do its re-review (step 5), then start no further round, because that much new text needs the user's design decision, not more fixes.
5. **Re-review** every round that applied a fix: step 3 of SKILL.md as a focused re-review, then step 4. When the round is already known to be the last (round 3, or past the growth limit), send the final full review (below) in the same message as this re-review: nothing is fixed after either, so running them one after the other only costs time. Append `## Round <n>` to the ledger with Edit: what was applied, declined or proposed, the new score, the table, and the updated To do list. A finding the re-review raises counts in that round's score until a later re-review calls it resolved.
6. **Stop** when the score is ≥ 8, when nothing left is yours to fix (only `needs-you`, `taste`, `declined`), when the growth limit is passed, or after round 3. There is no fourth round: what is still open after three rounds usually needs the user's decision rather than another edit, and each round costs a full critic run.

## Final full review

The round scores only say whether the fixes worked: focused re-reviews look at the changed lines, not at problems the first review missed. So after the loop stops (or beside the last re-review, step 5), spawn one more critic for a **full** review of the finished target (step 3 of SKILL.md without the focused re-review block), verify and score it (step 4), and append `## Final review` to the ledger. Do not fix its findings: list them for the user.

Delete `.vogon/.tmp/`. Final reply, first line: `Final full review: N/10 (rounds 2 → 6 → 9). Growth: 231 → 390 words.` For code, add `Tests: 90 passed, 15 skipped before; 96 passed, 15 skipped after.` or `Tests: not run (<why>): no code fix applied.` The final review's score is the target's score. Then what was fixed, the proposals to confirm, and the final review's open findings.
